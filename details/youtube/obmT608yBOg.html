2. 핵심 아키텍처 및 시스템 취약점 분석

A. BOLA(Broken Object Level Authorization) 취약점 메커니즘

OWASP API Security Top 10의 1위 취약점인 BOLA는 사용자가 로그인된 상태에서 /api/user/history?userId=123과 같은 요청 시, userId를 다른 사용자의 ID로 변경했을 때 서버가 해당 객체에 대한 실제 소유권(Ownership)을 검증하지 않고 데이터를 그대로 반환하는 결함입니다. 영상에 노출된 다이어그램에서도 잠금 해제된 조회 API 아이콘을 통해 다수 사용자의 프로필 카드로 연결되는 구조를 직관적으로 짚었습니다.

유출 피해 규모 및 항목 강남언니 로고 및 '약 22만 명 개인정보 유출' 언론 보도 화면, 이름/연락처/상담사진/의사명/시술내역/결제정보 포함 공지 텍스트 노출 단순한 개인정보를 넘어 민감한 성형 상담 사진과 시술 기록까지 통째로 유출된 매우 심각한 보안 사고라고 지적
원인 및 보안 권고 '권한 검증 취약점이 원인으로 추정됨' 안내 자막 및 API 권한 누수 인포그래픽 화면 제시 단순 조회 API를 허술하게 구현한 것이 화근이었으며, 개발자들은 API 개발 시 보안 검증을 각별히 신경 써야 한다고 강조

4. 실무 적용 및 엔지니어링 시사점

  • 객체 수준 인가(Object-Level Authorization) 미들웨어 적용: 모든 데이터 조회 쿼리 시 세션 또는 JWT 토큰에서 추출한 사용자 ID(current_user.id)를 WHERE 조건에 강제 바인딩하여 타인 데이터 접근 원천 차단.
  • 순차적 정수 ID(Auto-increment ID) 노출 지양 및 UUID/해시 ID 도입: 외부 API 엔드포인트 URL에 예측 가능한 시퀀스 ID 대신 무작위 UUID v4 또는 암호화된 토큰 식별자를 사용하여 열거 공격(Enumeration Attack) 방어.
  • 정기적인 API 침투 테스트 및 DAST/SAST 보안 점검 의무화: 배포 파이프라인에서 권한 누락 엔드포인트를 자동 탐지하는 보안 스캐너 연동.
